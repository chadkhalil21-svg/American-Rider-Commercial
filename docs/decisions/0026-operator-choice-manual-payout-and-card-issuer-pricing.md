# Founder decision: on-demand Operator payout choice (source candidate, not live)
Date: 31 October 2026

**Intent:** Do not automatically deposit Operators' money on Friday or another cadence by platform default. Operators should choose *when* to withdraw available funds, selecting a standard transfer or eligible Instant Payout. Normal completion continues to transfer 99% of gross Travel Fare plus eligible toll reimbursement into the **same Operator Stripe Express balance**. This is different from a bank payout. Preserve one existing Stripe account for a qualified Operator who also recruits; Recruiter commissions deposit to that same Stripe balance.

**Verification:** The live Stripe connection lists ZERO connected Operator accounts and ZERO platform bank payouts as of this review; there is no eligible real account on which to verify a Stripe Dashboard Pay out button, fee deduction or bank receipt. Backend source `connect-payout-schedule.js` currently defaults to Friday weekly automatic and `app/operator/withdraw.tsx` opens Stripe Express, not a native manual/instant bank payout action. Stripe Express documentation explicitly supports connected accounts selecting Manual and requesting Standard payout from the Balance tab *only when the platform has enabled those features*. Stripe manual payout holding limit for a US account is **2 years**, non-US generally 90 days. Sources: https://support.stripe.com/express/questions/how-do-i-manage-my-payouts and https://docs.stripe.com/connect/manual-payouts .

**Prepared source, gated:** `CONNECT_STANDARD_PAYOUT_INTERVAL=manual` now returns a manual payout schedule only when **both** explicit, separately verified controls are ON: `CONNECT_OPERATOR_CHOICE_PAYOUTS_VERIFIED=1` and `CONNECT_MANUAL_REFERRAL_RECONCILIATION_VERIFIED=1`. Otherwise existing live default remains weekly Friday and an attempted manual configuration fails safely. This PR does NOT turn on either flag, change any payout account, change connected Dashboard features, or provide a bank payout mechanism. The existing `applyAutomaticSchedule` interface is preserved to avoid accidental call-site changes.

**Why gated:** `recruiter-operator-transfers.js` still labels shared-account referral transfer as awaiting automatic bank payout and authenticates bank settlement with `payout.automatic === true` plus `reconciliation_status === completed`, neither of which applies to a manual payout. Manual payout does not provide an automatic payout's exact per-charge inclusion report. We must design an honest alternative ledger model based on provider-confirmed Transfer into Operator's Stripe balance, user-initiated bank payout, payout.paid/failure events, and verifiable cash balances, without claiming an individual commission is bank-paid merely from an unrelated payout. Do not silently make all manual bank payouts look like confirmed per-referral deposits. Manual payout trigger must not create a second Stripe account or secretly send someone else's money. Manual payee can request standard or Instant only where Stripe actually supports that account/destination.

**Required before activation:** In authenticated Stripe Connect Dashboard enable Express features *Manual payouts* and ideally *Edit payout schedule* as appropriate; verify a genuine connected account can see and use requested standard and eligible instant payouts; implement and test faithful referral-bank and provider-fee reporting for manual payouts, refund/failure/pending states and rate-limits; verify real per-recipient fee recovery once after provider invoices, and no second $2 monthly charge; ensure original Build 60 Operator screen's **automatic transfer** text is corrected through an appropriate signed UI release or verified safe web-only content (do not claim backend can silently edit existing native strings); confirm US manual holding-period and unclaimed-funds outreach with counsel. Preserving weekly default until these gates pass avoids trapping real earned funds in an account that cannot request them.

**Payment-card price truth:** `backend/fareauthority.js` deliberately sets `cardCountry=null` because Build 60 Stripe PaymentSheet permits the traveler to choose a NEW or different card only AFTER the server quote and PaymentIntent amount. `backend/payments.js` can read a SAVED payment method's issuer country, but the saved/default method is not guaranteed to be the one the traveler selects. Thus existing quote does NOT identify the actual charged card before price acceptance. For exact issuer-specific pricing, redesign the signed native checkout to select/bind a specific saved or newly tokenized Stripe payment method **before** server-signed fare quoting; re-quote and obtain affirmative Traveler approval if the method changes. For Apple Pay/Google Pay, confirm actual payment method details via Stripe's supported flow prior to a final amount where technically possible, otherwise use transparent worst-case pricing and never silently increase an already agreed Total. Authorized amount at booking must exactly match settled amount absent a separately agreed additional charge. A server-only flag cannot make the existing PaymentSheet reveal a future card choice.
