# ADR 0021 — Original Operator document available to the actual reviewer

**Decision (2026-10-15, prelaunch):** Repair the existing provider-neutral Operator onboarding exception path. No new insurer, screening vendor, subscription, county admission form, fare or payout decision.

## Verified source mismatch
An Operator's authenticated licence, registration or insurance photograph is uploaded under the private Cloudflare R2 `operator-documents/{uid}/...` key. The backend persists `users/{uid}.documents[kind].objectKey`, NOT the older public `imageUrl`. `readDocument` deliberately returns `review` for every automatic OCR result until independent verification. Operations can decide the exception, but its original page linked **only** `d.imageUrl`, leaving the human reviewer without the original evidence. This is a real broken end-to-end step, independent of successful synthetic eligibility tests.

## Correction and access restrictions
The authenticated Operations exception page now links to a same-origin private document viewer ONLY for a stored key belonging to that Operator. A named, MFA-backed Operations session is mandatory. The server re-reads that account's exact document reference, checks the kind and private key's owner, fetches the short-lived R2 signed GET **server-side**, rejects oversize (>5 MiB), upstream failure and unexpected file bytes, and sends only bounded PNG/JPEG/WebP/HEIC/PDF data with `private, no-store` and `nosniff`. The R2 signed URL is never put in HTML. Ordinary Operators, Travelers, unknown accounts and mismatched keys cannot use the view endpoint. Each acceptance/refusal still goes through the existing audited human decision and backend qualification rules. Automated proof added in `backend/operator-document-review.test.js`.

**Known separate UI gap:** The mobile "Choose a file" action currently opens `expo-image-picker`, which selects PHOTOS, not PDFs. R2 upload currently permits images only. This patch correctly restores viewing currently supported uploaded photographs; it does NOT claim PDF insurance selection/production upload works. Future PDF support needs native `expo-document-picker` installed with a regenerated lockfile, a private MIME-allowlisted R2 upload, bounded PDF inspection and an actual signed-device test. Until then the Operator can photograph the insurer declarations page or choose a screenshot; the interface must not imply it can open an arbitrary file.

## Capacity — measure before scaling
Source shows one Render Starter service (0.5 CPU / 512MB) and Firestore Standard's **free tier** of 50,000 reads / 20,000 writes daily (the production account billing plan and actual billed daily metrics remain unverified). The Operator presence interval is 90 seconds; with 100 Operators each on duty eight hours, the presence route alone could produce ~32,000 database writes/day. This is illustrative and excludes reads, GPS, booking, background tasks and other users. Firestore Blaze (usage billing with included free quota, provided billing is actually enabled) is the first required capacity purchase **if currently Spark**. It is not a faster processor and does not fix inefficient queries. Observe production billing/usage, event/latency and dispatch reads, establish low-cost alerting and representative isolated load testing; only then increase Render RAM/CPU/instances if backend CPU, memory or latency warrants it. Render instance scaling is distinct and Pro-tier autoscaling is not included with all workspace plans. No spend or Firebase plan change is performed by this ADR.
