# Paid-booking payment hold and Operator fee policy | October 19, 2026

**State of release: SOURCE PLAN AND TESTED POLICY; NOT A LIVE PAYMENT ROLLOUT.** This branch must not change existing charges to authorization-only until each backend money flow, mobile PaymentSheet, scheduled dispatch, webhook, refund, transfer and receipt state has been updated and reviewed together, then synthetic Stripe TEST mode accepted. Launch must keep taking real paid bookings under the present documented flow.

## Policy affirmed
1. Operators retain **99% of Travel Fare**; the $2.50 minimum Platform Fee is separate.
2. A Connect account with a bank/debit card payout incurs **$2 that month** under the currently selected Stripe-managed-by-platform pricing. No old 20-Travel waiver. No payout => no fee. The Operator pays via a separately disclosed and explicitly authorized charge; never change the 99% Fare share, silently reduce a bank transfer, or charge retroactively. Existing Operator accounts need separately recorded consent; server sweep must not bill when fee consent was given *after* the payout. A post-payout consent applies to **future payouts only**.
3. Standard Stripe Connect payout pricing is **0.25% + $0.25 per payout** under the platform-handled pricing model. Stripe also advertises **0.25% funds-routing** and **1% optional Instant Payout**. The 1% optional instant fee is borne by the Operator through their own Stripe choice. Owner directs that standard payout fees be passed through as well; **existing backend quotes still carry 0.5% plus 6¢ internal cost assumptions**, so passing them through has NOT YET been certified end-to-end. Do not remove that revenue provision or claim pass-through implemented without comparing actual Stripe account invoices, payout webhooks, user disclosure and a separate charge/reconciliation transaction.
4. A valid fee agreement requires affirmative voluntary confirmation and fee schedule in each supported language. The agreement is stored with a version and server timestamp. A new Stripe payout-account setup cannot proceed silently without consent. Existing Operators can accept separately. Do not condition earned payouts on post-hoc consent.
5. Receipt, payout and chargeback rights remain; consumer-lawful corrections must be honored even when inconvenient.

## Booking funds: source finding
- `backend/payments.js` creates a PaymentIntent with `automatic_payment_methods: {enabled:true}` and **no `capture_method:'manual'`**. Stripe's default automatically **charges the Traveler when they confirm**, not merely a hold. `backend/booking.js` requires PaymentIntent `status:'succeeded'` before dispatch; `backend/travelmoney.js` refunds a confirmed charge when eligible cancellation occurs. Merely changing the Stripe create option would break dispatch and truthful payment receipts. **Do not flip this one field independently.**
- For near-term Travels the eventual policy is: authorize eligible card for the all-in maximum, inspect `requires_capture` AND `capture_before`, dispatch only if sufficient authorization validity remains, capture **once** on recorded completed Travel, or capture only an evidence-backed disclosed cancellation/no-show fee if the cancellation is eligible. If a customer never received the service and no fee was earned, **cancel the authorization**, avoiding an actual refund. Show pending authorization truthfully; some issuer statements look similar to a debit.
- For far-future scheduled Travels the eventual policy is: **save a consented card via SetupIntent at booking without a monetary hold**, record the reservation and payment method securely; around **24 hours before start** attempt a fresh off-session authorization, send automated customer action request for authentication or a new method if needed, and **never dispatch without a confirmed hold**. If authorization fails, keep clear reservation state / notify with a reasonable deadline, then release assigned Operator fairly if not rectified. For near-term schedules within 24h, authorize promptly and verify expiry. Hold lifetime is NOT indefinitely extensible. Stripe says Visa merchant-initiated transactions may have only 4 days 18 hours; other brand/customer settings vary. **Read real `capture_before`**, never hardcode one 7-day guarantee. A second authorization requires explicit lifecycle, cancellation of previous hold, idempotency and customer disclosure; it is not a free evergreen hold.
- Existing `backend/scheduled-query-budget.js` and one-minute Google Scheduler provide a due-work mechanism, but do NOT currently implement the proposed saved-method preauthorization. Source-only `backend/payment-hold-policy.js` with synthetic negative tests captures future intended behavior, not an active flag.

## Cancellation, verified progress, consumer fairness
Current backend cancels free while awaiting/assigned/accepted and returns actual captured card money. A **$3 deduction is coded only from recorded `arrived` status**, and the server comments say route's arrival evidence was historically not integrated. Thus the prior Founder en-route fee is **not** delivered for an accepted Operator already driving. No invented payout can be collected. Proposed benchmark based on official Uber and Lyft: 2-minute free window after Operator accepts, THEN a transparent **up to $3 paid to Operator** only if server verifies meaningful progress toward pickup, with separate verified arrival/no-show rule; no fee before assignment, when Operator is at fault, delays/other operator failure, provider cancellation, or when progress evidence is unavailable. Show exact fee **before Traveler confirms cancellation**. Do not set a blanket no-refunds policy. Follow Florida consumer and transportation counsel's opinion on fee disclosure/fairness.

## Cost and infrastructure
- Resend Free observed **5/3000 monthly** and **0/100 daily** currently. Public price Free 100/day, Pro $20/50k emails/month no daily limit. Firebase Authentication email verification is a distinct Google service, with published Blaze verification quota up to 100k/day. The 100/day Resend ceiling constrains **our Resend-sent** insurance/broker messages, invitations, receipts and support, not necessarily each Firebase account registration.
- Render account lists 5 services: one $7 Starter Node API `American-Rider-Server`, plus 4 static websites including current main and preview. Paid API, Stripe and minute dispatch moved to Google, yet those static websites are still available on Render and the old backend may serve fallback links/legal pages. Keep until check live DNS, current web origin and OAuth redirect dependencies, then retire **only the unneeded paid API** and stop its automatic builds. Do not delete all static websites.
- Google Firestore source already uses geohash bounded pages and due-only schedules. Prior PR #138 removed rereads of a prefix. Avoid switching to Uber H3 without measured read/query savings and edge recall parity. Google's best practices prefer cursors to offsets and lowering *unused* index fanout. Do not relax duty freshness, safety or money evidence to save writes.
- Explicit single-Founder operational limits: routine risk/money exceptions queue and notification, no manual refund/payout activity except exceptional cases.
