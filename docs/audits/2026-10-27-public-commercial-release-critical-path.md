## Release execution order

1. **Freeze source scope:** merge only reviewed launch-critical patches with green exact-head CI (Google official mark; do not re-open known-good account deletion or button dimensions), await ongoing explicit QA fixes; inspect final before starting new signed binary.
2. **Finish public review package:** existing Founder review credentials, device demo covering real supported prelaunch state, written 2.1 answers; submit through App Store Connect Reply to App Review. Keep any non-commissioned features truthfully labeled and inaccessible without approved evidence.
3. **Resolve actual hard launch risks:** Florida insurer/legal eligibility structure, Apple account entity eligibility where required, live payment/transfer recovery after completed sandbox refund acceptance, signed device Operator/Traveler flows, Google Play location declaration. Assign evidence to an owner, state and source; do not swap PASS with NOT TESTED.
4. **Make one pinned replacement binary:** when code + native QA are complete, execute the existing controlled iOS workflow against exact current HEAD (not the old one-time pinned Oct22 workflow), confirm EAS submission/build number. If new iOS code is included, select Build 57 (or actual next unused version number) in rejected iOS 1.0.0 item, Add for Review, Resubmit to App Review. Keep Build 56 unchanged until replacement verified.
5. **Public commercial release only after approvals:** confirm Apple approved/published iOS app; Android Play Console verified Data Safety, background location and approval separately; only enable real money/Operator duty in jurisdictions and on accounts with actual qualification and legally adequate insurance. Continue to report Open/Blocked truthfully until then.

## Questions future audits MUST ask before claiming a pass
- *Which exact signed build and source SHA did the reviewer use?*
- *Did the official branding asset actually appear on a locked/offline handset?*
- *Are Apple and Google equally prominent, accessible and the same dimensions at 320/375/390/430pt and large text?*
- *Does a new person complete fresh sign-up, OTP/email, social sign-in, recent reauth, deletion for each linked provider and relaunch safely?*
- *What happens when provider API returns pending/refunded/failed/409/429/503, loses network, or sends a duplicate webhook?*
- *Can an actual eligible Operator lawfully be in service with correct liability coverage, including lapsed/insufficient policies, and can dispatch stay safe while phone sleeps?*
- *Does a reviewer have legitimate role-based access without fake approvals?*
- *Are all App Store/Google Play declarations, legal entity rights, and background location privacy terms verified in the actual account, not in GitHub?*
- *Does every revenue claim match settled provider identifiers and no undelivered transfer?*
- *Is the store app approved and available, rather than merely uploaded to TestFlight?*

**What the audit did NOT do:** grant platform insurance, sign a policy, create an Operator, charge an actual Traveler, upload a signed app, respond to Apple, publish an app, edit private App Store account metadata, or change Stripe/Firebase production permissions.
