## The narrow money-safety repair in this review

1. **Recovered scheduled PI:** Reattach the exact PI ID only after owner, Ride ID, amount, currency and capture-policy verification. Set `paymentCapturePolicy=manual_v1`, `authorizationState=held`, `authorizedAt` and `authorizedAmountCents`, **not** `paidAt`, for a live `requires_capture` hold.
2. **Expired/provider-canceled original PI:** Recovery, unlike dispatch, may identify an expired or already-canceled *correctly bound* original hold. Do **not** demand future capture eligibility to release it. It must never invent a fresh authorization, refund a nonexistent captured charge, or attach another Traveler's payment. Existing idempotent cancellation remains the remedy.
3. **Original captured PI:** Preserve the manual policy and exact captured amount, rather than silently reclassify the recovered PaymentIntent as a legacy auto-captured charge.
4. **Failed scheduled dispatch:** Record separate `authorizedCents` versus `chargedCents`, preserve the PI on the staged Travel, and create an accurate support case: **release held funds** vs **refund captured funds**. Upcoming screen shows neutral **Reservation needs review**, not the unverified **charged but not created** claim.
5. **Two-level tests:** Existing `bookingrecovery.test.js` gains provider-like held, expired and canceled PI recovery cases with no phantom `paidAt`, refunds, or repeat cancellation; `scheduled-manual-consent.test.js` enforces matching server/phone messaging and still checks consent-before-provider.

**Release discipline:** These repairs are source candidates until GitHub exact-head Release Gate, exhaustive, adversarial and Firestore checks pass. If merged, a controlled paid Cloud Run source deployment is necessary for backend parity; a GitHub merge is not a Cloud Run rollout. No new TestFlight without fresh Founder permission. No Stripe LIVE write or simulated 'real completed booking' may be claimed.

## Distinct operational acceptance, no extra infrastructure

P0 before public commercial launch: (a) one actual signed Traveler checkout and independently eligible Operator acceptance; (b) real collection on verified completion and one Stripe Connect transfer with recoverable failure; (c) card-hold expiration/3DS/scheduled dispatch/no-supply compensation; (d) exact installed build source parity, crash-free cold restart, wallets and app-review requirements. These are **external/system tests**, not missing foundational modules. P1: adult pickup code rollout with both apps ready, visible aged payment/dispatch cases until reconciled, accurate receipt/support and future reservation history. Keep security and legal qualification decisions separate from software test success.
