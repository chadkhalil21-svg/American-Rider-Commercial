## What was inefficient and what changes
Prior six-hour `sweepOperatorAccountFees` performed an unbounded read of **all accounts from the preceding month**, including paid, waived and failed accounts, then could attempt to charge a saved Traveler payment card. At 10,000 monthly accounts, 4 sweeps daily for 30 days is **1.2 million account document reads**, plus repeat writes/calls. This is workload multiplication, not a claim that invoices contain 1.2m billed reads. PR #182 stops wrong-wallet collection and full scans.

This stacked PR implements **event-triggered records**:
- Stripe signs `payout.paid` or `payout.failed`; verify webhook signature in existing provider-queue before handler, and take account identity from `event.account` (NOT `payout.destination`, which is a bank). Exclude platform's own bank payouts. No new clock or weekly schedule.
- Durable `operator_connect_payouts/<sha256(account,payout)> ` tracks each actual USD provider payout ID, operator, method, money amount, chronology and status. Exact duplicates write **nothing**. Out-of-order older events are ignored. A payout reported failed after paid reverses monthly count; same-second conflicts, unknown/legacy month history or changing IDs fail rather than charge fees. Keep payout failure support alert.
- Existing `operator_months/YYYY-MM/accounts/uid` now summarizes distinct paid payouts, not repeated naive "payoutSeen:true" writes. Legacy summaries without verified count require a one-time historical review. A positive payout count marks **awaiting provider fee evidence**, not `feeStatus=due` or `paid`; this intentionally **does not charge** any Operator.
- The six-hour maintenance task now checks only `operator_connect_fee_obligations` where `status=due` and `nextReviewAt<=now`, **max 2 pages of 80** using Firestore cursors and a single composite index in `firestore.indexes.json`. That queue is read-only; no remote card or connected balance charge and no read of thousands of settled accounts. With no actual verified fee obligations, the query is empty; Google documents minimum billed query reads, so do not claim absolute zero bill.
- The new event collection incurs an initial write per distinct payout plus a monthly summary update, which is a legitimate accounting event cost. Duplicates save repeat writes. The total net saving should be measured, not asserted as paid invoices. Staging requires index deployment before enabling updated backend.

## Google vs Uber H3 design
**Google Firestore:** Avoid offsets; use `startAfter` cursors; bounded `limit`; only status/nextReviewAt indexed for new due records; keep index fanout low, avoid global contention. For actual billing cost, run Firestore Query Explain on authenticated staging sample with 0/1/100/10k due and settled records and inspect `read_operations`, `index_entries_scanned`, execution duration, and query cost. We did not run Query Explain against live GCP here. https://firebase.google.com/docs/firestore/best-practices ; https://firebase.google.com/docs/firestore/query-data/index-overview
**Uber H3:** For dispatch, existing American Rider geohash 9-neighbor search already pages (40 then 80 more) and filters physical distance; H3 indexes hexagons but would require another stored field/index and potentially extra reads/writes. Do not migrate production until side-by-side matching, boundary coverage, real latency/charge benchmarks show clear improvement. https://www.uber.com/us/en/blog/h3/ ; https://h3geo.org/docs/ .
