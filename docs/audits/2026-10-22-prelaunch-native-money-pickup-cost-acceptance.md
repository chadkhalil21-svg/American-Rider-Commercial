## Binding Founder decision (21 October 2026): no mandatory adult PIN

**This section supersedes the previous draft rollout proposal below.** Normal adult Travelers do **not** need to request, display or hand over a six-digit code to begin a Travel. The Operator verbally confirms the Traveler's name at pickup, while the Traveler independently checks the Operator's name, vehicle and license plate in the app. Neither needs a new tap beyond the ordinary **Commence Travel** action; the server still owns the Travel status and checks current Operator assignment and pickup proximity. This decision was expressly reconfirmed by the Founder on 22 October.

**Teen Travel remains different:** the pre-existing private four-digit Teen code and Guardian safeguards remain required at pickup, with server rejection of unverified boarding. Do not weaken Teen verification or Operator eligibility checks.

**Specific corrections in this PR:** remove PR #222's unwanted adult PIN shortcut from live Traveler Travel; replace the adult code-request screen in Safe Travels with name/vehicle/plate guidance; remove the Operator's adult code input, redundant status lookup and verification request. Keep mandatory Teen code entry unchanged. This saves the extra adult pickup lookup and avoids per-pickup PIN data writes. Do **not** enable `ADULT_PICKUP_VERIFICATION` for launch or claim a coordinated adult rollout is needed. Dormant backend code does not mean an active feature or override the Founder policy.

**Published reference:** [Uber's rider safety tips](https://www.uber.com/us/en/ride/safety/tips/) recommend vehicle/plate matching and having the driver confirm the Traveler's name. [Uber Verify Your Trip](https://help.uber.com/riders/article/what-is-verify-your-trip?nodeId=9a2a4bc6-002b-4461-8e9e-8ea29974795d) is an **opt-in** adult PIN feature, not universally required. An iOS/Android app-binary acceptance test remains needed to confirm what the user actually sees; no new TestFlight without the Founder's authorization.

## Wallet truth
- On iPhone or iPad, Stripe PaymentSheet offers **Apple Pay** when the merchant and device are eligible. **Google Pay is not an iOS native wallet option**.
- On Android, the exact same authenticated Stripe PaymentSheet offers **Google Pay**, with `enableGooglePay:true` in Expo plugin and `testEnv` derived from the same server payment intent mode. The same per-platform distinction applies to saved-method SetupIntent.
- Credit/debit card entry remains the supported fallback. All-in Traveler Total is server-authoritative. A resumed `manual_v1` hold never opens a second PaymentSheet authorization.
- **Native binary acceptance still needs both platforms:** Apple Pay merchant setup/certification, Apple Wallet compatible device, Google Pay production access/testing where applicable, device credentials and issuer challenge handling. Source green is **not** device approval; Expo Go cannot validate Apple Pay/Google Pay. See [Expo Stripe](https://docs.expo.dev/versions/latest/sdk/stripe/), [Apple sandbox testing](https://developer.apple.com/apple-pay/sandbox-testing/), [Google Android wallet test checklist](https://developers.google.com/pay/api/android/guides/test-and-deploy/integration-checklist).

## Firestore read/write audit, decision
Existing: geohash cell retrieval uses at most nine prefixes per two tiers (and a bounded tail only if a prefix is saturated); a separate exact distance, screening, insurance and class matcher remains authoritative. A daily assignment remains examined for safety, but repeated identical `unanswered` writes are suppressed; a synthetic hour showed **60 prior marker writes vs one**. Scheduled queries are `status/atMs` due-only; waiting status writes are throttled; Founder `needs_attention` is fetched on demand 25+1, no cron, not a full-month scan; payout and refund durable state cannot be skipped.

**No new H3 index now.** Uber H3 is a useful hexagon hierarchy, not a substitution for authoritative matching, Firestore indexing, nor free reads. Migrating imposes extra Operator location writes, index and backfill obligations. Measure billed queries in Google Firestore Query Explain before deciding. Query Explain plan mode is itself billed at least one document read. Do not change duty heartbeat, GPS location cadence or actual safety polling without physical-device evidence. **No concrete further safe Firestore write omission was verified from this audit.** Read+write changes should be tied to measured volume, cost and safety regression rather than speculative micro-optimization. Sources: [Firestore best practices](https://firebase.google.com/docs/firestore/best-practices), [Query Explain](https://firebase.google.com/docs/firestore/query-explain), [H3](https://h3geo.org/docs/).
